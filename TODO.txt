❯ so are we actually collecting? or streaming?

We're collecting, and it's a necessary collect this time, not a style choice — here's why:

redaction_target_positions has to be fully materialized into an owned Vec<(usize, usize)> before the second loop starts, because that second loop calls events.split_at_mut(...) — a mutable borrow of events — while the first pass (events.iter().enumerate().filter_map(...)) holds an immutable borrow of events for its entire duration. Rust's aliasing rules forbid those overlapping; you can't be mid-iteration over events and mutate events in the same breath. Collecting into the small Vec<(usize, usize)> is exactly what ends the immutable borrow before the mutable one begins.

The difference from the original bug is what gets collected, not whether something does: before, it collected full LeanEvent clones (each owning a Value — arbitrarily large); now it collects a pair of usizes per redaction — negligible, fixed-size, no heap content copied. position_by_id (the HashMap<&str, usize>) is also a genuine, deliberate collect — it needs random-access lookup by ID, which is inherently a build-the-index-once structure, not something a streaming pass could replace.

Could this be made fully streaming (zero intermediate collection)? Not without unsafe (e.g. raw pointers to sidestep the borrow checker) — and this crate has unsafe_code = "deny" — so given that constraint, "collect the minimum cheap data needed, then mutate" is the correct, idiomatic-safe-Rust shape here, not a shortcut. ❯ are there any automated tools to help this kind of static code analysis??

Yes, a few, with real limits worth being upfront about:

- clippy::redundant_clone (in the perf group, which is already enabled in this repo's Cargo.toml) catches some of this — a clone immediately followed by a drop, or a clone where the original is never used again. It didn't fire on the ingest_events pattern because it can't: .filter(...).cloned().collect() isn't textually "redundant" to clippy — the original events is still used afterward, so from a pure ownership-analysis standpoint the clone looks legitimate. - Algorithmic complexity (the O(events × redactions) scan I just found) is fundamentally not lint-catchable at all. Clippy works on local, syntactic patterns; nested-loop cost across two different collections built at different points in a function is a whole-function reasoning problem. - Where a tool would actually catch this class of thing empirically: heap/allocation profilers — dhat-heaptrack (rust dhat-rs crate, drop-in global allocator that dumps an allocation profile) or valgrind --tool=massif, run against a synthetic large-batch ingest_events call. You're pointing at something real, not hand-wavy — it's called arithmetization, and it's the foundation of zk-SNARK circuit design. Every boolean/comparison operation has a polynomial encoding:

- AND(a,b) = a·b
- OR(a,b) = a + b − a·b
- NOT(a) = 1 − a
- XOR(a,b) = a + b − 2ab (or just a + b mod 2 over GF(2) — literally addition)
- Equality (a == b) → (a−b) = 0, and inequality is provable via multiplicative-inverse gadgets
- Range/threshold checks (PL ≥ level) → bit-decompose both values, then a sum of polynomial identity constraints over the bits
 So yes — the entire boolean circuit of auth checks can be flattened into a system of polynomial constraints — provably true, not a stretch.

Where I want to be precise, though: that's a different tool for a different job than what's already in rezzy. LtHash uses modular vector addition because it wants a commutative, order-independent accumulator for set membership (so two forks can compare state without replaying it). PinSketch uses GF(2^64) polynomials because syndrome decoding recovers the symmetric difference between two peers' sets. Neither is arithmetizing predicate evaluation — they're arithmetizing set representation. Arithmetizing the actual auth-check logic (PL comparisons, ban checks, branching) is the SNARK/STARK move, and its payoff is not a faster circuit — the circuit isn't faster to run: field arithmetic per boolean op plus proving-system overhead is almost always slower than just executing the native branch. The payoff is succinct verifiability: a server could prove it ran state resolution correctly on this DAG, and every other server checks the proof instead of redoing the whole graph walk. That's the actual reason this class of technique gets used, and it'd be a legitimately interesting direction for a homeserver — but it's a wholesale different subsystem (circuit definition, a proving/verifying key, either a trusted setup or a transparent one like STARKs), and rezzy has none of that machinery today.

❯ wait i'm confused? does this worsen or improe runtime?

Fair question — let me be precise, because it's neither a speedup nor really a "worsening" in the way that

For realistic room sizes (thousands to low millions of hashes): no measurable change. RoaringTreemap is BTrt shards indices by their high 32 bits. Since you're nowhere near 2^32 entries, everything lands in a single
shard (key 0), so every operation costs one BTreeMap lookup (basically free — one comparison against a sing through to the exact same RoaringBitmap code that runs today. Practically a no-op overhead.

What it actually changes: the ceiling, not the speed.
- Before: hard-capped at u32::MAX (~4.3 billion) distinct hashes — past that, try_build returns UniverseTooLarge and the audit can't run at all.
- After: capped at u64::MAX — a limit you will never hit in memory anyway (you'd run out of RAM to hold that many 16-byte hashes long, long before the index type became the bottleneck).

So this refactor isn't a performance change at all — it's a correctness/capacity ceiling fix: today, a storage backend with (hypothetically) more than 4.3 billion live node hashes gets a hard failure from the audit tool itself, unrelated to
whether it actually has the memory to do the audit. The swap removes that artificial failure mode. Nobody'shere near 4 billion HAMT nodes, which is exactly why the original assessment called itlow-value/impractical-to-test — it's closing a gap that's currently theoretical, not fixing something slow or broken today.

If anything, the only place you'd see a real (still tiny) cost is deep in RoaringTreemap's multi-shard set operations (|, &, -) if you ever did span multiple 2^32 shards — one extra level of tree traversal per op. At current scale that never
triggers.

So: runtime — unchanged in practice. What it buys you is headroom, not speed. Want me to go ahead with it anyway, given it's not a hot-path concern?

❯ would we panic or OOM tho with the new proposed scheme?

Neither, cleanly — you'd hit an OOM in both schemes (today's and the proposed one), and it would happen at  memory, long before the index-width ceiling (u32::MAX today, u64::MAX after) is ever reached.

Walk the actual memory cost: IndexedUniverse holds a Vec<StructuralHash> (16 bytes/entry) plus a HashMap<StructuralHash, u32-or-u64> (hash + index + hashmap bucket overhead, realistically ~40-50 bytes/entry with load-factor slack). At u32::MAX (~4.3 billion) entries, that's already ~170-220GB — no commodity machine has that. You'd exhaust RAM around a few hundred million entries on a typical box, which is nowhere close to 4.3 billion, let alone u64::MAX.

So a key thing this means for the refactor: the u32::MAX guard in the current code is already effectively dead code on real hardware — you can't practically get anywhere near it without OOMing first from the Vec/HashMap growth alone. Swapping
to RoaringTreemap/u64 doesn't change that; it just moves a ceiling that was already unreachable to one thats not "we used to panic there, now we OOM" — it's "we always OOM well before either ceiling, and the guardexists for symbolic completeness, not because anyone hits it."

What actually happens on the OOM itself, mechanically:
- Vec::push/HashMap::insert call the global allocator; on failure Rust's default behavior is to abort the process (not a catchable panic, not a Result you can handle) — no unwinding, no graceful exit. These are infallible allocations, so an OOM in try_build's Vec::push/HashMap::insert (which happens *before* the u32::MAX check) cannot be converted into UniverseTooLarge; only the index-overflow branch returns that error.
- In practice on Linux you often don't even get that: the kernel's OOM-killer sends SIGKILL to the process earlier, before an allocation formally "fails," under normal memory-overcommit behavior.

Either way: abrupt process death, not a controlled error path — same story before and after this refactor. If that's a concern, it's a pre-existing one (nothing in try_build streams or bounds memory as it counts), not something the index-width
change introduces or fixes. Worth knowing, but it's a separate hardening question from the one we were discussing. One related note for any future try_build rework: avoid allocating an extra HashSet on the overflow-return path (the current code builds one just to recount distinct hashes past the bound) — keep the existing UniverseTooLarge behavior for index overflow, but don't add a separate allocation to produce it.
