› should we define a new folder like biz or etc or lib or something to represent not state rez related stuff, but still outofband related?


• Yes. I would not put this under state, resolve, or auth; it is not state resolution logic.

  I’d use a domain name, not a generic bucket:

  src/out_of_band/
    mod.rs
    cuckoo_verify.rs
    server_keys.rs   // later, if needed
    minting.rs       // later, if this grows

  Then in src/lib.rs:

  pub mod out_of_band;

  And callers use:

  rezzy::out_of_band::cuckoo_verify::verify_minting_pow(...)

  I’d avoid names like biz, etc, misc, or lib. They become junk drawers quickly. out_of_band is explicit enough: this is adjacent Matrix machinery, but not state resolution.

  If you expect more PQ/server-key work, another defensible option is:

  src/federation/
    mod.rs
    server_keys/
      mod.rs
      cuckoo_verify.rs

  But for this repo, out_of_band is probably the better boundary because it says “not core state res” without overcommitting to a full federation stack.


› does this belong in its own micro-service backend?


• Probably yes, if this is intended for real key minting.

  For verification only, keeping it as a library is fine. Verification is cheap, deterministic, and useful inside homeservers/notaries.

  For minting/solving, I’d separate it:

  rezzy crate:
    verify embedded PoW
    derive key_id / short_key_id
    validate key object shape

  minting service:
    generate FN-DSA keypair
    search Cuckoo nonce/solution
    emit server key object
    manage CPU/GPU workers

  Reasons to split minting:

  - It is expensive and operationally different from request handling.
  - It may need GPU/large-memory workers or native solver binaries.
  - It has different failure modes, queues, progress reporting, cancellation, and rate controls.
  - It touches private key generation/signing, which benefits from tighter isolation.
  - Homeservers and notaries need verification, but usually do not need to mint often.

  I would not make verification a microservice. That adds latency and another dependency to a hot path. Keep verification as an in-process Rust library.

  So the clean split is: library verifier in rezzy or a small shared crate; separate minting backend/service for creating keys and PoW stamps.
