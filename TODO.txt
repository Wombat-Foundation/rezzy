❯ wait i'm confused? does this worsen or improe runtime?

Fair question — let me be precise, because it's neither a speedup nor really a "worsening" in the way that

For realistic room sizes (thousands to low millions of hashes): no measurable change. RoaringTreemap is BTrt shards indices by their high 32 bits. Since you're nowhere near 2^32 entries, everything lands in a single
shard (key 0), so every operation costs one BTreeMap lookup (basically free — one comparison against a sing through to the exact same RoaringBitmap code that runs today. Practically a no-op overhead.

What it actually changes: the ceiling, not the speed.
- Before: hard-capped at u32::MAX (~4.3 billion) distinct hashes — past that, try_build returns UniverseTooLarge and the audit can't run at all.
- After: capped at u64::MAX — a limit you will never hit in memory anyway (you'd run out of RAM to hold that many 16-byte hashes long, long before the index type became the bottleneck).

So this refactor isn't a performance change at all — it's a correctness/capacity ceiling fix: today, a storage backend with (hypothetically) more than 4.3 billion live node hashes gets a hard failure from the audit tool itself, unrelated to
whether it actually has the memory to do the audit. The swap removes that artificial failure mode. Nobody'shere near 4 billion HAMT nodes, which is exactly why the original assessment called itlow-value/impractical-to-test — it's closing a gap that's currently theoretical, not fixing something slow or broken today.

If anything, the only place you'd see a real (still tiny) cost is deep in RoaringTreemap's multi-shard set operations (|, &, -) if you ever did span multiple 2^32 shards — one extra level of tree traversal per op. At current scale that never
triggers.

So: runtime — unchanged in practice. What it buys you is headroom, not speed. Want me to go ahead with it anyway, given it's not a hot-path concern?

❯ would we panic or OOM tho with the new proposed scheme?

Neither, cleanly — you'd hit an OOM in both schemes (today's and the proposed one), and it would happen at  memory, long before the index-width ceiling (u32::MAX today, u64::MAX after) is ever reached.

Walk the actual memory cost: IndexedUniverse holds a Vec<StructuralHash> (16 bytes/entry) plus a HashMap<StructuralHash, u32-or-u64> (hash + index + hashmap bucket overhead, realistically ~40-50 bytes/entry with load-factor slack). At u32::MAX (~4.3 billion) entries, that's already ~170-220GB — no commodity machine has that. You'd exhaust RAM around a few hundred million entries on a typical box, which is nowhere close to 4.3 billion, let alone u64::MAX.

So a key thing this means for the refactor: the u32::MAX guard in the current code is already effectively dead code on real hardware — you can't practically get anywhere near it without OOMing first from the Vec/HashMap growth alone. Swapping
to RoaringTreemap/u64 doesn't change that; it just moves a ceiling that was already unreachable to one thats not "we used to panic there, now we OOM" — it's "we always OOM well before either ceiling, and the guardexists for symbolic completeness, not because anyone hits it."

What actually happens on the OOM itself, mechanically:
- Vec::push/HashMap::insert calls the global allocator; on failure Rust's default behavior is to call handlhe process (not a catchable panic, not a Result you can handle) — no unwinding, no graceful exit.
- In practice on Linux you often don't even get that: the kernel's OOM-killer sends SIGKILL to the process earlier, before an allocation formally "fails," under normal memory-overcommit behavior.

Either way: abrupt process death, not a controlled error path — same story before and after this refactor. If that's a concern, it's a pre-existing one (nothing in try_build streams or bounds memory as it counts), not something the index-width
change introduces or fixes. Worth knowing, but it's a separate hardening question from the one we were disc type).

What's already streaming: walk_reachable_node_hashes (src/hamt/delta.rs:501) is push-based — it takes a marool callback and calls it per-node as it walks, never buffering a list of reached hashes internally.
bitmap_reachability_audit cleverly reuses the reachable: RoaringBitmap itself as that callback (RoaringBitmnewly added," which doubles as the dedup/visited check and the output — no separate "seen" set). So thereachable side costs only what the RoaringBitmap needs to hold, which is compact by design.

What isn't streaming — the actual memory hog: IndexedUniverse::try_build (audit.rs:76). It eagerly drains the entire universe iterator into a Vec<StructuralHash> + HashMap<StructuralHash, u32> before anything else runs. That's the one full-size, random-access structure in the whole audit, and it's unavoidable in this design because assigning dense indices "first-seen order, O(1) lookup either direction" fundamentally needs either full materialization or an external index.

To actually stream it, you'd need to give up the "arbitrary-order input, O(1) random lookup" property and p

1. Push index assignment onto the storage layer, persistently. If whatever backs universe (your node store)ash→id mapping incrementally as nodes are written (an on-disk table, not rebuilt per audit), then the auditnever builds IndexedUniverse from scratch — it just opens a cursor over the existing mapping. This is thady a storage layer under HAMT nodes; it turns "rebuild dense index every audit" into "reuse dense indexstorage already maintains." Best option if it fits your architecture — ask if rezzy's storage layer already has something like this.
2. External sort + merge, if there's no persistent index: require/produce universe in sorted-by-hash order an't give it pre-sorted), and have the reachable side also emit into a sorted-on-disk structure as it walks. Then compute reachable/unreachable as a single streaming merge pass — O(1) extra memory (just the current item from each stream), O(n log n) extra I/O for the sort. This is the classic answer when you truly can't hold the working set, but it's a real architectural addition (temp files, an external sort), not a small patch.
